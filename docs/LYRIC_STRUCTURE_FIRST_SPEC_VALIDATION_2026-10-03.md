# 構造を基準にする歌詞表示仕様の検証 — 2026-10-03

**「構造に沿って表示し、音声認識と本文で何を表示するかを決め、その他の全解析を補助に使う」という方針は、仕様として成立しますわ。** 全曲で確認した結果、現在の行ごとの表示を維持でき、複雑な重み付けや一律の近傍補正を必須にする必要はありません。

## 対象・作業種別・根拠

対象は「ありがとうを歌にのせて」の全320.8秒・元の歌詞64行です。取得済みのMusic Understanding全6種類、全文Apple Speechの628トークン、保存中の位置を使用した仕様成立性の検証です。再解析・音声認識の再実行はしていません。

大きな区間19、小さな区間32、フレーズ65を調べました。全フレーズがそれぞれ1つの小さな区間・大きな区間に収まり、3階層をそのまま保持できます。

## 成立する役割分担

| 情報 | 使用する役割 |
| --- | --- |
| 大きな区間・小さな区間・フレーズ | 曲のどのまとまりにいるかを決め、表示の枠とまとまりの切替に使う |
| 全文音声認識＋入力した歌詞本文 | その枠の中で表示する元の行と、行ごとの切替を決める |
| vocal/drums/bass/otherの検出範囲・活動量 | 歌声の変化と伴奏の変化を区別し、認識との対応を補助確認する |
| 拍・小節・BPM | 音楽上の位置と前後のつながりを確認する |
| Pace・Key | 周辺の勢いや調性の変化を確認する |
| momentary/shortTerm/integrated/peak | 局所の音量変化と曲全体の基準を確認する |

その他の解析も同じ区間で照合します。変化していないKeyなどを理由に時刻を動かす必要はありません。すべてを同じ点数で混ぜる必要もありません。

Appleの公式説明でも、構造は3階層、活動量は楽器の存在・強度、Paceは音楽の勢いとして提供されています。これらの意味に沿って役割を分ける整理です。[Apple公式説明](https://developer.apple.com/videos/play/wwdc2026/253/)

## 全曲で確認した結果

個別行の選択を確認するため、既存の本文との対応から得た補正前の認識区間を、交差するすべてのフレーズへ関連付けました。フレーズと行の全境界で曲を分け、表示状態の異なる全161区間を調べています。局所だけを抜き出した確認ではありません。

| 検査 | 結果 |
| --- | --- |
| 元の本文・ID・順序の保持 | 64/64行で保持 |
| 行区間と構造枠の対応 | 64/64行を覆える |
| 関連フレーズ数 | 1つ：16行、2つ：46行、3つ：2行 |
| 歌唱中として選ばれる行の同時重複 | なし。最大1行 |
| フレーズ切替による行の途中欠落 | なし |
| 全6解析の区間文脈 | 全65フレーズに記録・確認 |
| 対応する歌詞のないフレーズ | 1〜4、65 |

元の1行が複数のフレーズをまたぐ場合も、その行を続けて表示できます。フレーズが変わっただけで、歌詞を消したり、先頭から表示し直したりする必要はありません。

歌詞に対応しない初めの4フレーズと最後の1フレーズにも歌声活動はありました。したがって、「歌声があるから歌詞を出す」という処理にせず、音声認識と本文の対応で表示する内容を決める仕様が成立します。

構造の範囲は0.831〜320.783秒です。その外側には対応する歌詞がなく、曲の0秒へ架空の歌詞開始を追加する必要はありませんでした。

## 同じフレーズに複数行が入る場合

45.363〜50.314秒のフレーズ10には、7行目「ひとつひとつの瞬間が」、8行目「大切な宝物」、9行目の冒頭が入ります。

本文と認識の対応では、7行目45.42〜47.40秒、8行目47.40〜49.98秒、9行目49.98秒からです。**構造の枠を保ち、その中で7→8→9行目へ切り替えれば済みます。** 3行を同時に表示することや、全行の開始・終了をフレーズの端へ固定することは、この仕様の必須条件ではありません。

現行の表示処理は歌唱中の行と前後のフェードを最大2行まで表示します。この行ごとの選択方法と両立します。[現行表示処理](/Users/apple/Desktop/Dev_App/Music_Understanding_Prayer/Sources/Lyrics/LyricMotionView.swift:34)

比較検証で、認識runを最も長く重なる1フレーズだけへ関連付け、それ以外を表示候補から除く方法も確認しました。この方法では10行の端が枠の外へ出ます。交差するすべてのフレーズに関連付ける方法では、欠落を生じませんでした。単一フレーズへの無理な固定は採用しません。

## 0.00何秒という差の扱い

数msの差だけで不合格にしたり、別の行を選んだり、行を途中で消したりする必要はありませんわ。完全な数値一致を合格条件にはしません。

歌詞同期の知覚を調べた研究でも、先行・遅延の違いやリズムの影響があり、固定の秒数だけでは表示の良し悪しを説明できません。この資料から「何ms以下なら誰にも分からない」という一律の値を決めることもできません。[歌詞同期の知覚を調べた研究](https://archives.ismir.net/ismir2021/paper/000052.pdf)

今回の検証でも、約10⁻¹⁴秒のJSON加算の差を丸めとして扱い、表示状態の不一致には数えていません。これは数値計算上の扱いです。0.50秒を一律の補正幅や許容誤差にする根拠は、今回の仕様にはありません。
